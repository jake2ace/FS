# FreightSentinel（中文说明）

**航运单据核对 —— 从一个共享收件箱，到一份差异报告。**
Averis x Monash Hackathon 2026 参赛作品（Shipping Document Verification 赛题）。

**在线原型：** https://fs-two-sand.vercel.app/

> English version: **[README.md](README.md)**

系统读取业务共享收件箱，先把邮件分成五类；对每一封「要求核对提单」的邮件，读取 Shipping Instruction（SI）
与 Draft Bill of Lading（BL），按语义对齐七个字段，**准确指出哪里不一致**，并把原文证据放在旁边。
凡是不能安全判断的情况（缺附件、附错文件、文件读不出、字段是空值），一律带着原因转人工，绝不猜。

```
官方收件箱 → 智能分类 → 分析（提取 + 比对） → 风险雷达 → 人工复核 或 安全完结
```

### 自己跑需要注意

**这个仓库里没有 API Key，也不可能有。** 把代码拉到本地可以启动、可以打开界面、可以读到随包的邮件，
但**每一次分类和比对都会失败并显示一个明确的技术错误**，直到你把自己的 key 写进 `backend/.env`：

```dotenv
AI_PROVIDER=deepseek
AI_API_KEY=<你自己的 DeepSeek key>
AI_MODEL=deepseek-flash
```

这是有意为之：密钥是服务端机密，不进仓库、不下发浏览器、不打印进日志。完整变量清单见
[第二节 环境变量](#二环境变量重点)，运行命令见[第三节 本地运行](#三本地运行)。

**想看系统真正在跑，请直接用上面那个在线链接** —— 它已经配置好，而且结果已经在里面了。

## 一、技术架构

```
浏览器 ──> Next.js 前端 (Vercel) ──/api/*──> FastAPI 后端 (Render) ──> 文件解析 (txt/pdf/docx/xlsx)
                                                    │              ──> AI 供应商 (DeepSeek 等)
                                                    │              ──> AI 结论 + 结构/证据校验
                                                    └──> 结果缓存 (JSON)
```

**浏览器永远不直接调用 AI，也永远拿不到 API key。** 前端在服务端把 `/api/*` 转发给后端，
key 只以环境变量的形式存在于后端服务器上。

| 层 | 技术 | 职责 |
|---|---|---|
| 前端 | React + Next.js 14 (TypeScript) | 今日工作台、智能收件箱、案件详情、复核队列、批量运行 |
| 后端 | Python 3.11 + FastAPI + Pydantic | 收件箱读取、分析流程、批量运行、人工决策、官方格式导出 |
| 解析 | pdfplumber / python-docx / openpyxl | 附件取文，PDF 带版面感知（粗体标签 / 正常值） |
| AI | 单一供应商，JSON 输出，直接 HTTPS | 邮件意图与分类、文件类型与七字段提取（带证据） |
| 比对 | AI 结构化返回 | 语义比对、单位换算、七个匹配标记与最终状态 |
| 校验 | Python / Pydantic | 返回结构、字段完整性、原文证据、状态与明细是否自洽 |

**业务判断全部由 AI 负责**：分类、认文件、提取七字段、理解同义词与单位、比对、给出最终状态和证据。
Python 只负责读文件和校验返回（结构、证据、自洽性），不自己算业务结论，也不覆盖 AI 的读数。
AI 返回不合格 → 转复核。没配 AI 或调用失败 → 显示为技术失败并可重试，**不会退化成规则跑出一个假的 OK**。

#### 为什么由 AI 判断，而不是规则引擎

我们一开始的方案正好相反：**规则为主，AI 兜底**。改变主意，是因为想清楚了那套规则实际上会学到什么。

题目给的邮件和文件来自一个**模板生成器**。针对它们写的规则可以把分数做得很高 —— 但它认出来的是
**那个生成器**，不是提单。它能处理的每一种排版，都是有人事先选定的排版。真实环境里只要出现一个标签
写法不同、字段顺序不同、地址跨页续排的文件，就落在所有已写规则之外；而**规则引擎的失败方式不是提问，
是给出一个自信的错误答案**。在这个数据集上刷出高准确率，几乎说明不了在下一个数据集上的准确率 ——
而后者才是航运团队真正用得上的那个准确率。

自己训练模型是另一条路，**而这个数据集本身就是否决它的理由**。训练要划算，前提是数据量和多样性足够
教会模型一些通用模型还不知道的东西。这 520 封邮件两样都不满足，训练出来的只会是**第二种、而且更弱的
过拟合同一个生成器的方式**。

剩下的选择就是：用一个本来就理解航运单据怎么写的模型去读它们。所以业务判断全部交给 AI，而程序做
程序真正擅长的那部分 —— 读文件、校验模型返回是否结构合规、检查每一条引证是否真的出现在原文里、
不合格就拒绝。**没有任何规则会在 AI 失败时悄悄补上一个结论**，因为在报告上，规则跑出来的 `OK` 和
核实过的 `OK` 长得一模一样 —— 而这份报告的全部价值，恰恰在于它们不一样。

这个选择的代价我们照实写：每封邮件一次模型调用，耗时以秒计而不是毫秒，而且要付费。一条确定性管线
在这个数据集上会更快也更便宜 —— 它同时也在**测量一件错的事情**。

### 云架构

三个云服务，每一个都在做产品离不开的工作。

| 组件 | 服务 | 在这里实际做什么 |
|---|---|---|
| 判断层 | DeepSeek API | 所有业务判断。两套不同的模型配置构成分级决策路径：主判用 `reasoning_effort=high`，第一遍不肯下结论的案子才用 `max` 再判一次。 |
| 后端 | Render（免费 web service） | 管线、收件箱 API、批量运行、人工决定与官方格式导出，由 `render.yaml` 以 Blueprint 方式部署。 |
| 前端 | Vercel | 工作台，静态预渲染并由边缘节点分发，`/api/*` 在服务端转发到后端，浏览器永远拿不到密钥。 |

**云是核心功能，不是托管。** 这个产品没有规则引擎，也没有离线模式：供应商不可达时，案子会变成一个
显式的技术失败并转给人，不存在任何本地路径能产出判断结果。分级复核同样是一个云设计 —— 两套不同
思考深度的模型配置，第二套只在第一套拒绝下结论时才调用。最近一次全量运行里是 42 次资深调用对
742 次主判，也就是说更慢更贵的那一档**只在首轮停下来的地方付费**，不是对全部 520 封都付。

**基础设施即代码。** `render.yaml` 固定 19 个环境变量 —— 供应商、两级模型、思考强度、超时、限速、
降级行为和批量并发。部署时只索取一个值 `AI_API_KEY`，标记为 `sync: false`，永不进入仓库。结果是：
线上服务可以从这个仓库完整重建，并且可以证明它跑的就是被测试过的那套配置，而不是某次在面板上点出来的状态。

**是按云供应商的限制来写的，不是绕过它。** 滑动窗口限速器按模型限制每分钟请求数；批量并发有上限；
HTTP 429 与 503 会让主模型进入冷却窗口并切到备用模型；重试次数有上限，不会对一个不可用的回答反复索取；
模型输出被截断时会被识别并转人工，而不是当成有效判断去解析。

**运维闭环。** Render 对 `/health` 做健康检查，该端点同时支持 `GET` 与 `HEAD`（uptime 监控默认发 HEAD）。
外部监控每 5 分钟轮询一次，顺带避免免费实例休眠。`/health` 分别报告服务、数据与 AI 三种状态，
所以「页面是绿的但供应商挂了」是能被区分出来的。

#### 当前档位的代价，以及怎么扩

服务最初跑在 Render 免费档，现在是 Standard（1 CPU / 2 GB）加 1 GB 磁盘。下面同时列出迁移的原因
和仍然存在的限制。

| 限制 | 今天的影响 | 下一步 |
|---|---|---|
| 单实例 | 挂了磁盘的服务不能跑多个实例，部署也不再是零停机 | 这是主动接受的取舍：结果存储在进程内，第二个实例会持有同一份状态的另一个副本，两边会分叉。要解除这个限制得换成托管 Postgres，那在未来路线里，不在本版本中。 |
| 免费档的 512 MB 内存 | 同时解析多份 PDF 时 `BATCH_CONCURRENCY` 只能压在 4，跑完一轮要 16 分 24 秒 | 迁到 Standard 后解决：同一轮在并发 32 下只要 3 分 39 秒，**没有改任何应用代码**。 |
| 模型延迟（现在的地板） | 并发从 32 提到 64 只省下 4%。CPU 基线约 5%、内存不超过 20%，说明瓶颈不在实例 | 一轮的耗时不可能低于其中最慢的那一封 —— 一次主判加一次资深复核，这条链天然是串行的。只有换一个**不需要想那么久**的模型才能缩短它。 |
| 免费档的休眠 | 冷启动看起来像原型坏了 | 付费实例已经消除；uptime 监控保留。 |

全量跑目前是进程内的 asyncio 批处理。把它放到队列 + 独立 worker 之后，重启可以续跑而不是失败，
提高吞吐也变成加 worker 而不是在单实例里拉高并发。这是下一块自然的云架构，预赛版本里是**有意不做**的。

## 二、环境变量（重点）

所有配置都从环境变量读取。
- **本地**：复制 `backend/.env.example` 为 `backend/.env`，在里面填。该文件已被 `.gitignore` 忽略，**不会进仓库**。
- **云端**：**不要上传 .env 文件**，把值填到平台的 Environment Variables 面板里。

> ⚠️ **API key 只放后端服务器（Render 的环境变量面板）。**
> 不写进代码、不写进仓库、不写进前端、不打进日志。前端知道的东西，任何访客都能看到。

### 后端变量（填在 Render → 服务 → Environment）

| 变量 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `AI_PROVIDER` | ✅ | `none` | 用哪家：`deepseek` / `openai` / `anthropic` / `gemini` / `none` |
| `AI_API_KEY` | ✅ | – | 供应商密钥。**只填在这里**，仓库里永远是空的 |
| `AI_MODEL` | – | 各厂默认 | 比赛配置 `deepseek-flash`；默认值见 `app/config.py` |
| `AI_MODE` | – | `full` | `full` = 所有判断交给 AI（正式配置）；`off` = 停用分析 |
| `AI_THINKING` | – | `false` | 主模型是否开启思考，比赛配置 `true` |
| `AI_REASONING_EFFORT` | – | `high` | 思考强度 `low` / `high` / `max`（`medium` 等同 `high`） |
| `AI_TIMEOUT` | – | `60` | 单次调用超时（秒），建议 `240` |
| `AI_FALLBACK_MODEL` | – | – | 主模型 429/503 时的同厂备用模型；`none` = 不启用 |
| `AI_MAX_RPM` | – | 各厂默认 | 每分钟请求上限；`0` = 不限速（付费额度） |
| `BATCH_CONCURRENCY` | – | `4` | 批量跑全收件箱时的并发数 |
| `AUTOMATION_POLICY` | – | `standard` | 给 AI 的复核尺度 `standard` / `strict`，不是写死的置信度门槛 |
| `CORS_ORIGINS` | – | `*` | 允许直连 API 的来源；前端走服务端代理，一般不用管 |
| `AI_SENIOR_PROVIDER` | – | `openai` | 资深复核阶段用哪家 |
| `AI_SENIOR_MODEL` | – | – | 资深复核模型；**留空 = 关闭该阶段** |
| `AI_SENIOR_API_KEY` | – | 复用 `AI_API_KEY` | 只有跟主模型不同厂时才需要单独填 |
| `AI_SENIOR_THINKING` | – | `false` | 资深阶段是否开思考 |
| `AI_SENIOR_REASONING_EFFORT` | – | `high` | 比赛配置 `max` |
| `AI_SENIOR_TIMEOUT` | – | `120` | 资深阶段超时（秒） |
| `AI_SENIOR_MAX_RPM` | – | 推导值 | `0` = 不限速 |
| `PYTHON_VERSION` | Render | `3.11.9` | `render.yaml` 里已经写好，不用手填 |

## 三、本地运行

**后端**（Python 3.11）：

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env          # 然后在 .env 里填 AI_API_KEY
uvicorn app.main:app --reload --port 8000
# 打开 http://localhost:8000/health  和 http://localhost:8000/docs
```

`app/config.py` 会自动读取 `backend/.env`；真实环境变量优先级更高，所以同一份代码在 Render 上不用改。

**前端**（Node 18+）：

```bash
cd frontend
npm install
BACKEND_URL=http://localhost:8000 npm run dev
# 打开 http://localhost:3000
```

**测试**（只用假模型，不花钱）：

```bash
cd backend && AI_PROVIDER=none AI_MODE=off .venv/bin/pytest -q tests
```

## 四、云端部署（给负责部署的队友）

### 第 1 步：后端部署到 Render

1. 打开 [render.com](https://render.com) → **New +** → **Blueprint**
2. 选择这个仓库（`jake2ace/FS`），Render 会自动读取根目录的 `render.yaml`
3. Render 只会问你要 **一个** 值：`AI_API_KEY`
   —— 粘贴密钥（**队长单独发给你，不要贴到任何聊天群或提交到仓库**）。
   其余全部变量（供应商、主模型与资深模型、思考强度、超时、限速、并发）都写死在 `render.yaml` 里，
   不用手填，也不会漏填 —— 保证云端跑的就是本地测过的那套配置。
4. 点 Deploy，等构建完成
5. 验证：浏览器打开 `https://<你的服务名>.onrender.com/health`
   —— 返回里能看到服务状态、数据包状态、AI 配置状态

> 免费套餐 15 分钟没流量会休眠，第一次唤醒要 30–60 秒。
> 评审当天建议用 UptimeRobot 之类的服务每 5 分钟 ping 一次 `/health` 保持唤醒。
> `render.yaml` 不安装 Tesseract/Poppler，所以云端没有 OCR 兜底能力。

### 第 2 步：前端部署到 Vercel

1. 打开 [vercel.com](https://vercel.com) → **Add New** → **Project** → 导入同一个仓库
2. **Root Directory 一定要设成 `frontend`**（不设会构建失败）
3. Environment Variables 加一条：
   `BACKEND_URL` = `https://<你的服务名>.onrender.com`（结尾不要带斜杠）
4. Deploy

`next.config.mjs` 里的 rewrite 会在**服务端**把 `/api/*` 转发到后端，
所以浏览器不需要 CORS，前端打包产物里也不会出现后端地址或密钥。

### 第 3 步：换 key / 撤销 key

密钥只存在两个地方：Render 面板 + 本地被忽略的 `backend/.env`。
要换只需在 Render 改值并重新部署，仓库和前端一个字都不用动。

### 部署常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| Vercel 构建失败 | Root Directory 没设成 `frontend` | 改设置后 Redeploy |
| 页面打开空白 / 请求 500 | `BACKEND_URL` 没填或带了结尾斜杠 | 改成 `https://xxx.onrender.com` |
| 第一次请求很慢 | 免费套餐休眠唤醒 | 正常，等 30–60 秒；评审前先手动唤醒 |
| `/health` 显示 AI 未配置 | `AI_PROVIDER` / `AI_API_KEY` 没填 | 在 Render 面板补上后重新部署 |
| 分析大面积失败 | 密钥额度用完或被限流 | 查供应商额度；必要时调 `AI_MAX_RPM` |

## 五、结果约定

| 情况 | status | review_reason | 界面表现 |
|---|---|---|---|
| 七个字段全部一致 | `OK` | – | 无差异 → 可安全完结 |
| 至少一个字段不一致 | `MISMATCH` | – | 高风险，列出 `defect_fields` 及 SI / BL 两边的值 |
| 要求比对但没附件 / 只有 SI | `NEEDS_REVIEW` | `missing_attachment` | 转人工 |
| 第二个附件是发票 / 装箱单 / 证书 | `NEEDS_REVIEW` | `wrong_doc_type` | 转人工 |
| 文件为空 / 损坏 / 纯图片 | `NEEDS_REVIEW` | `unreadable` | 转人工 |
| 必填字段是空值或占位符 | `NEEDS_REVIEW` | `missing_value` | 转人工 |
| 只是要求「发出」草稿提单，还没附件 | `OK` | – | 「待发送 Draft BL」行动清单，不进复核队列 |
| 其他类别邮件 | `OK` | – | 无需处理 |

空值或无效值**不算差异**。七项比对必须全部可靠完成，才会给出 OK 或 MISMATCH。

### 为什么「要求发出草稿提单」报 OK，而不是 NEEDS_REVIEW

这是上面这张表里唯一一处需要我们自己拿主意的地方，影响 220 封比对邮件中的 91 封，而且它是一个
**决定**，不是一个测量结果。完整理由如下：

**这些邮件到底在要求什么。** 它们没有要求我们核对任何东西，而是要求我们**发出**一份草稿提单，
好让对方之后去核对。没有附件，是因为这个阶段本来就不该有附件。流程还没走到比对那一步，
不是比对失败了。

**为什么不报 `NEEDS_REVIEW`。** 这个状态的含义是「系统判断不了，需要人来决定」。可这里没有任何
东西需要决定：没有文件迟到、没有东西丢失，人读完这封邮件得出的结论和系统一模一样。把这 91 封
全部送进复核队列，只会把真正需要人处理的那 20 封埋在 91 封「打开看一眼就关掉」的邮件底下 ——
而消除这种噪音，正是这个产品存在的理由。

**为什么 `missing_attachment` 这个原因在这里是错的。** 这个原因描述的是：本该收到的文件没有收到，
导致比对做不下去。可这些邮件里，本来就不该有任何文件。把它们记成一次失败的比对，等于在报告里
写下一件没有发生过的事。

**我们不太确定的地方。** 官方 contract 把 `OK` 定义为「七个字段全部一致」，而这里根本没有字段可以
比，所以 `OK` 也不是完美契合。封闭词表只有三个值，没有一个的含义是「这个请求不涉及比对」。我们
选了那个**不会凭空造出一个问题**的值，同时确保界面从不掩盖这个区别：这 91 封出现在专门的
**待发送 Draft BL** 清单里并附上该做的动作，绝不会被算进「已核实的比对」。如果主办方的本意是要
把它们当成转人工，改动量是 `backend/app/pipeline.py` 里的一个分支加 `backend/app/ai.py` 里的一段
提示词。
文件角色绝不靠文件名猜。

确认版流程见 [流程图](docs/FreightSentinel-确认版流程图.html)、
[SVG 版](docs/FreightSentinel-确认版流程图.svg) 与 [流程说明](docs/确认版流程说明.md)。

## 六、更正副本与人工复核

对已确认的 MISMATCH，可以「生成更正版 BL 副本」：在**另一个文件**里只改不一致的字段，
用 AI 从 SI 提取的值；保存前 AI 必须重新读取生成出来的文件、确认七个字段。
PDF 编辑保守处理：位置不明、字体不支持、重叠、空间不够，一律报告为需要人工编辑，不保存未经验证的副本。

- `PENDING_HUMAN_APPROVAL`：复核过的副本或人工报告等待采纳
- **采纳并保留副本**：校验文件哈希后保留，采纳本身不再调用 AI
- **拒绝并删除副本**：只删除后端生成的那份副本，原件不动，审计记录保留
- 人工可以补交替换的 SI/BL 附件，或直接修正七项读数；最终人工表单可以完全不依赖 AI 完成处理
- 人工处理后禁止再自动分析；重开由人决定
- 未知类别会一直留在人工队列，并阻止「完整导出」

生成的文件在 `backend/.cache/revisions/<email_id>/<revision_id>/`；
结果、人工复核历史与批量历史都存在 `CACHE_DIR` 下（已 gitignore）。

## 九、验证记录

下面是 2026-09-21 核对过的当前云端快照，运行链路为：浏览器 → Vercel → Render → DeepSeek。
这组数据取代旧的 61 / 48 / 111 快照；旧快照产生时，界面还没有把待发送 Draft BL 的行动请求单独分开。

| 当前云端运行 | 结果 |
|---|---|
| 处理邮件 | 520 / 520 |
| 耗时 | 16 分 24 秒（并发 4） |
| Batch 失败 | **0** |
| 首轮 AI 调用 | 742 次，**0 失败** |
| 资深复核调用 | 42 次，1 次技术失败（超 token 上限） |
| 非比对邮件（只分类） | 300 |
| 安全完成的比对 | 63 |
| 待发送 Draft BL 的行动请求 | 91 |
| `MISMATCH` | 46 |
| `NEEDS_REVIEW` | 20 |

当前被分类为 `BL_COMPARISON` 的 220 封邮件，在界面中分成：63 个安全比对、91 个 Draft BL 行动请求、
46 个不一致和 20 个转人工。完整官方导出包含另外 300 封非比对邮件，因此最终 status 分布是
454 个 `OK`、46 个 `MISMATCH`、20 个 `NEEDS_REVIEW`。

这 20 个转人工案件分布在四种允许的原因上。最近一次完整运行是 `missing_attachment` 6、
`missing_value` 5、`unreadable` 5、`wrong_doc_type` 4；同一套管线、同一个收件箱，更早的运行得到的是
5 / 5 / 5 / 5。我们如实写出这个波动，而不是挑一个看起来最整齐的数字。它是真实的，幅度很小，而且有
明确的成因：这里面有几封邮件本身就卡在两种原因的边界上 —— 附件收到了但读不出来、某个字段是缺失而
不是对不上 —— 让语言模型在其中挑一个标签，它不会每次都挑同一个。每次运行都稳定不变的，是真正承重
的那部分：520 封已分析、220 个比对、20 个交还给人工。

这次运行的早期快照曾经是 9 / 5 / 4 / 2，原因是：资深复核因技术原因失败时，会用笼统的 `unreadable`
交接结果覆盖掉主判已经得出的结论。技术失败不是业务结论，所以现在的升级路径会**保留主判结论**，
并把资深复核的失败单独记录在旁边。`email_507` 就是本次运行中仍然撞上资深复核 token 上限的那一封：
它保留了主判给出的 `missing_attachment`，并带有警告「Senior review did not complete ...
The primary finding was kept.」。这个回归由 `backend/tests/test_senior_handoff.py` 覆盖。

我们从未打开过主办方的标准答案，所以这里任何一种分布都不等于正确性证明。它能说明的是：没有任何
一种原因压倒性地占多数 —— 这正是一个刻意构造的边界案例集应有的形状；而当初正是那个歪掉的
9 / 5 / 4 / 2 让我们发现了上面那个 bug。

**吞吐与并发。** 耗时取决于模型调用的延迟，不取决于我们的代码。跑完整个收件箱 —— 520 封邮件、
786 次模型调用 —— 需要 3 分 39 秒，后端绝大部分时间都在等供应商返回。`BATCH_CONCURRENCY` 是唯一的
调节位，也正是当前这套部署形态的原因：在 512 MB 的免费实例上、并发压到 4 时，同样这一轮要跑 16 分
24 秒，因为内存装不下同时进行的多份 PDF 解析。换到 Standard 实例后这个位调到 32 —— 不改任何应用
代码，提速 4.5 倍。附件解析被派发到线程池而不是跑在事件循环上，所以把这个位调高换来的是真正的并行，
而不是让任务排在某一次解析后面。速度本身不是评分项；它在这里重要，是因为一个 520 封邮件的收件箱
必须能在五分钟的视频里演示完。

`GET /api/submission` 的输出与主办方 `sample_submission.json` 逐字段核对过：520 个 email_id 不缺不多，
每条记录五个字段完全一致，类型一致。

**两种导出，对应两种读者。** `GET /api/submission` 是给机器核对的：一封邮件一条记录，形状由主办方
规定。`GET /api/export.csv` 是给运营人员的：**一个不同的字段差异就是一行**，SI 和 BL 的读数并排列出，
不用打开应用就能从上往下处理。没有差异要处理的案件也会占一行（字段列留空），所以这份文件仍然
对每一封邮件都有交代。文件带 UTF-8 BOM，否则 Excel 会把非 ASCII 的港口名和公司名读成乱码 ——
而这份文件恰恰就是给会用 Excel 打开它的人准备的。

**这证明了什么、没证明什么。** 它证明管线能在真实基础设施上完整跑完、失败是显式可见而不会被悄悄
当成通过、结果可以跨环境复现。它**不能**证明业务判断的准确率 —— 我们没有读取标准答案，下面列出的
已知问题也尚未解决。

## 十、遇到的挑战

**字段标题 ≠ 字段值 —— 当前运行已修复。** 邮件 383、411、498 曾把 `To the Order of:` 与
`Consignee:` 的标题差异误判成值不同。当前部署已把三封全部判为 `OK`，并说明标题写法不同、实际公司
值一致。

**技术失败不能覆盖掉有效发现 —— 已修复。** 资深复核超过模型输出上限时，原本会用笼统的
`unreadable` 把案件交给人工，顺手丢掉首轮已经得出的、更准确的原因。**安全转交本身不够 —— 如果
转交过程毁掉了已经掌握的信息，那仍然是退步。** 现在资深复核因技术原因失败时，会保留首轮结论，
并把这次失败单独记录在旁边。回归测试见 `backend/tests/test_senior_handoff.py`。当前运行中仍有
一次资深复核撞上上限（`email_507`），而这封现在保留了它的 `missing_attachment`。

**人工保存进度不该改写原因 —— 已修复。** 记录部分人工处理时，会把案件原有的原因一律写成
`missing_value`。保存进度不是一个新的发现，所以现在保留已经确立的原因。

**拒绝猜测是设计，不是异常分支。** JSON 解析失败、引用的证据在原文里找不到、字段没给全 —— 每一种
都会被校验拒绝，带着原因转人工。这里的诱惑是「退回规则算一个结果出来」，但系统不这么做：对看报告
的人来说，**规则跑出来的 `OK` 和真正核对过的 `OK` 长得一模一样**，这比没有结果更危险。

**本地与云端的配置漂移。** `AI_SENIOR_PROVIDER` 的默认值是 `openai`。部署时如果不填它，资深阶段的
供应商就与主模型不一致，密钥不会被复用，**整个二次复核会自己关闭，而且不报任何错** —— 服务显示健康、
输出看起来正常，跑的却是另一套没被测试过的流程。现在所有变量都写死在 `render.yaml` 里，部署不可能
再悄悄偏离测试过的配置。

**冷启动和「原型挂了」长得一模一样。** 免费套餐 15 分钟无流量就休眠，之后第一个请求会返回 30–60 秒的
503，界面显示「0 emails」—— 跟一个坏掉的系统毫无区别。解决办法是用外部监控每 5 分钟 ping 一次
`/health`，让服务在评审窗口内始终保持唤醒。

**结果曾经每次部署都消失 —— 已修复。** 免费套餐没有持久磁盘，实例文件系统里的那一份就是唯一一份：
重新部署或重启就会丢掉一次已完成的运行，全量跑到一半往 `main` 推一次代码更是直接销毁它。现在服务跑在
付费实例上，挂载了 1 GB 持久磁盘（`/var/data`），`CACHE_DIR` 指向磁盘内部，因此结果、人工决定、生成的
BL 副本和补充文件都能挺过重启。这件事的教训是：**「在没人部署之前它是好的」不算一个能用的原型。**

## 十一、未来路线

**建立权限控制系统。** 目前后端的写接口是完全公开的：任何知道地址的人都能触发全量重跑、修改人工
结论或清空结果。演示阶段可以接受，真实使用不行。下一步要做的是一套完整的访问控制——登录与身份、
按角色区分能做什么（只读的旁观者、能做决定的操作员、能改配置的管理员）、写操作限流，以及一份记录
「谁在什么时候改了什么」的审计日志。读接口也不该所有人都能访问：这里面是客户名称、货物和港口。

**让状态跨越单个实例。** 持久磁盘现在已经能让结果存储、BL 副本和补充文件挺过重启，但它仍然是
**一个进程独占的一份 JSON 文档**，这也正是服务无法扩到多实例的原因。下一步是托管 Postgres：那才是
历史记录、审计轨迹和人工结论真正该待的地方，也是上面那套权限系统存用户和角色的地方。它**有意不放进
预赛版本** —— 它会改变服务的启动方式，而一个做了一半的版本，比一个诚实写出来的限制更糟。

**读更难的文件。** 在后端主机上装 Tesseract 与 Poppler，启用管线里已经实现、但当前 Render 环境缺少
系统依赖而无法使用的本地 OCR 兜底；并评估用视觉模型处理扫描件与纯图片页。

**接真实邮箱。** 用 IMAP 或 Microsoft Graph 替代静态数据包，让系统直接读运营邮箱，而不是读一份
交付过来的数据集。

**支持自己上传邮件。** 现在的收件箱就是交付过来的那份数据集，界面上没有任何添加入口 —— 一个团队
想拿它跑自己的积压邮件，只能去服务器上改文件。要做的是一条上传通路：把 `.eml` 文件或整个文件夹拖进
浏览器，校验后写入服务现在已经挂载的磁盘，再走**和数据包完全相同的附件解析管线**；同时要能把不同
批次隔离开，避免一次上传覆盖掉另一次。它之所以放在这里而不是放进本版本：**预赛评分跑的是指定的
那 520 封邮件**，上传功能对这件事提供不了任何证据，而一个做了一半的上传功能，只会给真正被评估的
部分带来风险。

**让复核队列产生复利。** 每一次人工更正都已经记录了确认后的类别、结论、差异字段和处理说明。把这些
回流成评测用例，复核队列就变成一套**随使用量增长的回归测试集**。

**建立可度量的基线。** 把全量运行和结构化验收脚本放进 CI，任何提示词或模型的改动都要先和上一轮的
完整结果逐封对比再决定是否采纳，而不是靠跑一两个样本拍脑袋。
