> 记录日期：2026-09-21

> 用途：内部复盘 + 提交材料中 "Challenges faced" 部分的素材来源。

## 一、判断质量类问题（最核心）

### 1.1 自动化转化率过低：91 封邮件被无谓地转人工

**现象**
520 封邮件全量跑完后，精确率没有问题，但有 91 封被判成 `NEEDS_REVIEW / missing_attachment`，全部转给人工。人工队列被这 91 封淹没，真正需要人看的案子反而被埋掉了。

**诊断过程**
1. 先把这 91 封的正文按模板分组，发现它们高度同质——都是「请把 draft BL 发过来给我们核对」这一类请求。
2. 回头逐句读提示词，定位到一句话：把「应该在这里的文件不存在」定义得太宽，导致模型把「还没开始比对」也算成「比对失败」。

**根因**
这类邮件根本没有东西可比——对方是在要我们发出草稿 BL，不是在说附件丢了。它既不是比对成功，也不是比对失败，而是流程还没到比对那一步。原提示词里没有给模型第三种出路，模型只能往 `missing_attachment` 靠。

**解决**
改写 `backend/app/ai.py` 的提示词，明确区分两种情况：
- 邮件要求**比对** SI 与 draft BL，而文件缺失 → `missing_attachment`
- 邮件要求**发送** draft BL 以便日后核对 → 没有任何东西丢失，报 `OK`，`review_reason` 为 null，把收件人该做的动作写进 `suggested_action`

**教训**
提示词里定义一个类别时，必须同时说清楚「什么不属于这个类别」，否则模型会把所有说不清的情况都塞进最近的那个标签。

---

### 1.2 提示词改对了，结果反而更糟：91 封全变成 `unreadable`

**现象**
上一条改完重跑，91 封不但没有变成 `OK`，反而全部变成了 `NEEDS_REVIEW / unreadable`——比改之前更差。

**诊断过程**
关键证据有两条：
1. 结果里的 `decision_method` 是 `response_validation`，说明拦下它们的不是 AI，是程序的校验层。
2. 记录里 AI 自己的 `unconfirmed_ai_assessment` 是**正确的** `OK`——模型判对了，判完被程序推翻了。

**根因**
`pipeline.py` 的 `_validate_response` 里有一条硬性规则：只要 AI 报了 `OK` 或 `MISMATCH`，就必须存在一份可读的 SI 和一份可读的 BL，否则视为模型胡说，强制降级。这条规则本身是对的（防止模型在没看到文件时瞎判），但它不知道「请求发送草稿」这种情况压根就不该有文件。

**解决**
把邮件的 `intent` 一路传进 `_validate_response`，加一个旁路：

```python
awaiting_draft = v.status == 'OK' and not docs and intent == 'request_draft'
if not awaiting_draft and v.status in ('OK','MISMATCH') and (...):
    raise ValueError('AI successful comparison requires one readable SI and one readable BL.')
```

**教训**
改了提示词之后，一定要检查程序侧的校验层是不是也需要同步放行。AI 判对了却被自己的校验层否掉，从最终结果上看跟 AI 判错一模一样，很容易误诊。

---

### 1.3 把字段标签当成字段值来比

**现象**
少量案子被判成 `MISMATCH`，但人工核对后两份文件其实一致。

**根因**
`To the Order of:` 和 `Consignee:` 是同一个字段的两种印刷写法。模型把标签文字本身也算进了比较内容，于是认为两边不同。

**解决**
提示词里加一条明确规则：印刷标签不属于字段值，只比较标签后面那部分内容，绝不能仅凭标签措辞不同就报差异。

---

### 1.4 分类提示词的长期迭代

分类提示词从 v2 一路改到 v7，每一版都跑预检 + 补充测试 + 全量测试，把对照结果落盘到 `docs/` 下（`分类提示词v3~v6-*.json/csv`）。主要解决的是：

- 误导性主题行覆盖正文真实意图
- 「批量提醒提交 SI」属于 `GENERAL` 还是 `SI_REQUEST` 的边界
- 要求模型先输出证据原文、再给类别、最后给理由，避免先下结论再找理由
- 证据必须是正文里逐字连续的原文，不许改写、不许加省略号

**最终结果**：连续两次 520 封全量跑，五个类别的分布、进入比对的封数、差异与转人工的数量都保持一致；两次运行的逐封结果都完整落盘，可以复查。

## 二、界面与可用性类问题

### 2.1 用了题目里没有的词：`High risk`

题目给的封闭词表只有 `OK / MISMATCH / NEEDS_REVIEW`，界面上却自创了一个 `High risk`。评委对不上。
**解决**：全部改名为 `Mismatch`，与官方词表一致。

### 2.2 `等待 draft BL` 方向搞反了

原本写的是「等待对方发来 draft BL」，但实际业务方向相反——是**我们**要把 BL 发出去。文案把责任方写反了，看界面的人会等错东西。
**解决**：改名为 `Draft BL requested`，并把「该做什么」写进卡片。

### 2.3 改了名字，两个计数器漏改，磁贴显示 0

重命名之后，统计逻辑里还在按旧字符串匹配，磁贴数字变成 0。
**解决**：在 `schemas.py` 里定义唯一常量 `DRAFT_REQUESTED_UI`，`store.py` 和 `pipeline.py` 都引用它，杜绝字符串散落各处。

### 2.4 引导的方向错了

第一版引导是「告诉用户去哪里改数据」，但真实场景里人要做的是**决定**，不是**修改**。而且如果还没跑过检测，第一步应该是先跑检测。
**解决**：重做成随状态变化的引导条（没跑检测→提示跑检测；跑完→直接指向最该先看的那一件），并新增优先处理面板，把「先处理哪个」标出来，文案统一改成「已经帮你排好序 / 由你来决定」。

### 2.5 图例单独列一块不好看

**解决**：改成直接在图上标注（direct labelling），去掉独立图例框，加引导线连接。

### 2.6 饼图标签顶部被裁切

**诊断**：把同一套几何计算在容器里渲染成 PNG，自己看图才发现顶部溢出（纯读代码看不出来）。
**解决**：标签防重叠算法加上顶部钳制和底部溢出回推两段逻辑。

### 2.7 Chrome 自动翻译把界面译成乱码

Chrome 检测到英文界面自动翻译，把 `Status` 译成「地位」、`Session` 译成「会议。」、`Draft BL` 译成「选秀 BL」，和项目自带的中英切换叠加成一团乱。
**解决**：`layout.tsx` 加 `translate="no"`、`className="notranslate"`、`other: { google: 'notranslate' }`。

### 2.8 翻译字典重复 key 导致编译失败（发生两次）

`LanguageProvider.tsx` 的英译中字典里出现重复 key，TypeScript 直接编译不过。
**解决**：每次改字典必须跑一次去重检查再编译。另外发现带数字的动态字符串无法整体翻译，必须把数字和文字拆成两个节点。

### 2.9 批量编辑时删错了代码块

用 Python 按字符串切片改 `page.tsx` 时，因为新插入的 JSX 里含有和锚点相同的字符串，切到了错误的位置，删掉了不该删的代码。
**解决**：改用唯一的多行锚点定位，并在改完后立刻编译验证。

## 三、部署与运维类问题

### 3.1 Render 从不自动部署

`render.yaml` 里写了 `autoDeploy: true`，但实际 push 之后从来不触发。
**解决**：接受现状——每次后端改动都必须手动 `Manual Deploy → Deploy latest commit`。并写进 README，避免队友以为推了就生效。

### 3.2 UptimeRobot 一直报 Down（405）

保活监控每次请求都返回 405。
**根因**：UptimeRobot 默认发 `HEAD` 请求，而 FastAPI 的 `@app.get` **不会**自动支持 HEAD（Starlette 的 `Route` 会，FastAPI 的装饰器不会）。免费版 UptimeRobot 又不允许改请求方法或自定义可接受状态码。
**解决**：从根上改后端——`@app.api_route("/health", methods=["GET", "HEAD"])`，`/api/health` 同样处理。

### 3.3 Render 免费版会休眠

免费实例 15 分钟无请求就休眠，冷启动要等很久，演示时很危险。
**解决**：UptimeRobot 5 分钟间隔保活（monitor id 804046058）。另外免费版每月 750 实例小时，保活是够用的。

### 3.4 `CACHE_DIR`：先是绝不能配，后来变成必须配

本地 `.env` 里的 `CACHE_DIR` 是 Mac 的绝对路径，直接搬到 Render 上会崩。
**当时的解决**：`render.yaml` 固定 19 个环境变量但**不包含** `CACHE_DIR`，并在注释里写明原因。

**后来这条结论被推翻了。** 挂上持久化磁盘之后，结果缓存必须写到磁盘挂载点里，否则实例一重启
就全没了 —— 于是 `CACHE_DIR` 从「绝不能配」变成「必须配成 `/var/data/cache`」。

真正咬人的不是这次反转，而是**改了没生效**：Blueprint 的环境变量不会因为推代码而同步。我们推了
新的 `render.yaml`，Render 照常部署了代码，但 `BATCH_CONCURRENCY` 还是旧值、`CACHE_DIR` 压根不存在。
表面上一切正常，只有耗时不对。我们是靠算出来的 —— 实测每秒 0.69 次模型调用，反推并发仍然是 4，
才发现环境变量根本没应用。**解决**：这两条都在 Render 的 Environment 面板里手动填，不要指望
`render.yaml` 会覆盖已经存在的服务。

**教训**：Blueprint 只在服务**创建时**读一次环境变量。之后改 `render.yaml` 里的变量等于没改。

### 3.5 环境变量太多，队友配不对

**解决**：改用 Render Blueprint，`render.yaml` 里把所有参数写死，只留 `AI_API_KEY` 一条 `sync: false` 需要在面板手填。特别注明 `AI_SENIOR_PROVIDER` 必须和 `AI_PROVIDER` 一致，否则复核阶段会静默关闭（不报错，只是不工作，很难发现）。

## 四、Git 与凭据安全

### 4.1 沙箱环境访问不了 GitHub

开发环境的代理拦截了 GitHub（403），所有 `git push` / `git pull` 必须在本机终端里跑。
**解决**：所有远程操作改成「生成命令 → 本人在终端执行 → 截图确认」的协作方式。

### 4.2 残留的 `.git/index.lock`

一次 `git add --dry-run` 被中断，留下锁文件，后续所有 git 操作被阻塞。
**解决**：申请删除权限后清理。

### 4.3 `&&` 命令链断在中间

`git add -A && git commit && git push` 这种链条，当 `git commit` 遇到「没有改动可提交」时返回非 0，后面的命令全部不执行，但看起来像是卡住了。
**解决**：拆成单条命令依次执行。

### 4.4 contributor 列表里出现了 AI 署名

提交信息里的 trailer 让 GitHub 把 AI 列进了贡献者。
**解决**：`git filter-branch --msg-filter` 批量去掉 trailer，配合 `--force-with-lease` 推送。

### 4.5 凭据被贴进对话（两次）

一次 GitHub PAT，一次 Google Gemini API key。
**解决**：立即吊销并重新生成。确认 `.gitignore` 里 `.env` 与 `.env.*` 全部覆盖，密钥只存在于本地 `.env` 和 Render 的 Environment 面板，从不进仓库、不进前端、不打印到日志。

## 五、Gemini 3.8 Flash 适配尝试（2026-09-21，未成功）

这是提交前最后一次技术尝试，**结论是暂不切换**，记录完整过程备查。

### 5.1 动机
希望换用 Google `gemini-3.8-flash`，沿用现有的两段式设计（主判用第二档思考强度，资深复核用最高档）。

### 5.2 发现的问题：Gemini 分支根本没接思考配置

检查 `backend/app/ai.py` 时发现，`thinking` 和 `reasoning_effort` 这两个参数**只在 DeepSeek 分支里生效**。Gemini 分支是最早写的占位实现，只发了 `temperature` 和 `maxOutputTokens`。

直接切过去的后果是：
- 「第二档 + 高档」的配置没有任何地方能生效
- 两段式复核退化成「同一个模型、同样的参数、跑两遍」，复核完全失去意义
- 没有截断检查，模型输出被截断时会当成正常结果吞掉

### 5.3 适配实现

查证 Google 官方文档后（思考参数在 2026 年已从 `thinkingBudget` 改为 `thinkingLevel`），重写了 Gemini 分支：

| 项目 | 实现 |
|---|---|
| 思考强度 | `generationConfig.thinkingConfig.thinkingLevel` |
| 档位映射 | 项目 `high` → Gemini `medium`（第二档）；项目 `max` → Gemini `high`（高档） |
| 关闭思考 | 用 `low`（`gemini-3.8-flash` 不支持 `minimal`，传了会报错） |
| 输出预算 | 开思考时提到 32768（思考 token 与答案 token 共用同一额度） |
| 采样参数 | Gemini 3 系列拒收 `temperature`，自动不发；2.x 老模型照发 |
| 旧模型兼容 | `gemini-2.x` 不认 `thinkingLevel`，自动降级用 `thinkingBudget` |
| 截断检查 | `finishReason == "MAX_TOKENS"` → 抛错转人工 |
| 思考摘要 | 跳过 `thought: true` 的 part，只取真正的答案文本 |
| 空回复 | 被安全策略拦截等情况会明确报错，不返回空字符串 |

用伪造的 HTTP 响应跑真实代码路径验证，六条路径（主判档位、复核档位、关思考、旧模型、截断、空回复）全部符合预期。

### 5.4 三次实测，三种失败

| 次数 | 配置 | 结果 |
|---|---|---|
| 第一次 | 6 封邮件，并发 2 | 脚本写死「必须是 DeepSeek」，直接退出 |
| 第二次 | 同上，脚本已改为 provider 无关 | 12 次调用全部 `402 Payment Required`——该 Google Cloud 项目未开通结算，`gemini-3.8-flash` 不在免费额度内 |
| 第三次 | 充值后重跑 | 39 次调用，34 次 `503 Service Unavailable`（5 次成功，分类正确，证明接口本身完全可用） |
| 第四次 | 3 封邮件，并发降到 1 | 21 次调用，20 次失败（95%）——排除并发因素 |

期间还观察到一条 pypdf 的 `EOF marker not found` 警告，是某个 PDF 附件缺少标准结束标记，属于正常警告，不影响解析。

### 5.5 结论与决策

**代码是正确的，付费也已开通，失败原因在 Google 服务端容量。** 请求发送完全正确，5 次成功调用证明了这一点，其余是对方拒绝服务。

考虑到：
- 现有 DeepSeek 配置已经连续两次全量跑复现，结果稳定
- 距离预赛截止不足 12 小时，视频尚未录制
- 换模型后必须重跑 520 封全量验证，至少 20 分钟，且质量未知

**决定：预赛维持 DeepSeek 配置不变。** Gemini 适配代码已合并进仓库并保留，`.env` 的 Gemini 版本备份为 `backend/.env.gemini.bak`，一条命令即可切换。

**后续：如果进入决赛，再重新评估是否切换到 Gemini 3.8 Flash**——届时需要重新测试 Google 服务端的可用性，并完整跑一次 520 封全量对比两边的准确率，用数据决定，而不是凭偏好。

## 六、耗时调优：从 16 分钟到 3 分半，以及为什么到此为止（2026-09-22）

### 6.1 起因

有竞品在同一套 520 封数据上号称 3 秒跑完。读了对方仓库后判断那是确定性/模板管线 —— 不调模型，
自然快。我们的每一个业务结论都来自模型，没有规则兜底，所以不可能到那个量级。但 16 分钟确实太慢：
演示视频只有 5 分钟。

### 6.2 三次实测

| 配置 | 并发 | 耗时 |
|---|---|---|
| Render 免费版（0.1 CPU / 512 MB） | 4 | 16 分 24 秒 |
| Standard（1 CPU / 2 GB）+ 1 GB 磁盘 | 32 | **3 分 39 秒** |
| 同上 | 64 | **3 分 30 秒** |

第一步提速 4.5 倍，**第二步只提速 4%**。并发翻倍几乎没有效果 —— 这是整件事的转折点。

### 6.3 Render 实测指标（30 分钟窗口，覆盖上述运行）

| 指标 | 实测 | 上限 |
|---|---|---|
| 内存 | 峰值约 20% | 2 GB |
| CPU | 基线约 5%，峰值 45% / 60% | 1 CPU |
| 磁盘 | 约 1% | 1 GB |
| 请求量 | 30 分钟 1,509 次，期间 CPU 仍在基线 | — |
| 实例数 | 1 | — |

**CPU 基线 5% 说明这台机器绝大部分时间不在计算，而在等供应商返回。** 内存离上限差了 4 倍。
也就是说：实例从来就不是瓶颈，再加并发只是让更多请求同时排队等待。

### 6.4 尾部现象与成因

观察到的现象是：**前 500 封不到一分钟跑完，最后 20 封要花掉两分半。**

成因在管线结构里：

- 520 封中约 474 封只需 1 次模型调用（约 9 秒）
- 约 46 封会升级，需要第 2 次：资深复核（`thinking=true`、`reasoning_effort=max`）
- **信号量是按「整封邮件」持有的** —— 一封邮件从主判到资深复核结束，始终占着一个槽位

并发 64 时 46 次升级可以全部并行，于是整轮耗时的下限就等于**最慢那一封的耗时 = 一次主判 + 一次
资深复核**。这是一条串行链，它无法与自己并行，所以并发调到多少都穿不过去。实测 3 分半，离这个
下限只差约 30 秒。

最后剩下的 20 封，恰恰就是最终仍为 `NEEDS_REVIEW` 的那 20 封 —— 连资深复核都没能定案的案件，
自然也是它思考最久的案件。**尾部慢不是缺陷，是双层判定的代价本身。**

### 6.5 评估过但否决的方案：关掉资深复核的思考

考虑过保留 `reasoning_effort=max`、把 `AI_SENIOR_THINKING` 关掉。读代码后发现**这个档位不存在**：

```python
payload["thinking"] = {"type": "enabled" if self.thinking else "disabled"}
if self.thinking:                                       # 只有这里面
    payload['reasoning_effort'] = self.reasoning_effort  # max 才会被发送
```

`reasoning_effort` 只在 thinking 开启时才会发给 DeepSeek。关掉 thinking 等于 `max` 静默失效，
资深复核退化成一次普通的非推理调用 —— 它就不再是「质量不同的第二意见」，只是换了个提示词再掷
一次同样的骰子。**双层判定的全部意义都在这里，所以否决。**

### 6.6 结论：下一步提速要换的是模型，不是参数

剩下的时间几乎全部是资深复核的思考回环。在这条路上只有两种缩短方式：

1. **调低 `reasoning_effort`** —— 让它想得更少。快，但第二意见的质量随之下降，架构叙事塌掉。
2. **换一个更强的模型** —— 让它**不需要**想那么久就能达到同等质量的第二意见。

只有第二种在不损害设计前提的情况下缩短回环，**所以真正的下一步是升级复核模型，而不是继续拧参数**。
我们尝试过的 Gemini 3.8 Flash（见第五节）正是这个方向，只是当时供应商侧没跑通。

需要说明的是：这两种改动**都会改变那 20 个边界案件的判定结果**，因而都需要重跑全量并重新核对所有
对外数字。这也是它被推到赛后再做的原因。

### 6.7 顺带确认的一件事

持久化磁盘经过重启验证：手动重启服务后，520 条结果仍在。Standard 这一档的回报不是速度
（速度被模型延迟锁死了），**而是评审期间实例重启不会让评委看到一个空仪表盘**。

## 七、方法论沉淀

这个项目里真正起作用的几条做法：

1. **先分组再定位**。91 封误判不是一封封看出来的，是按正文模板分组后，一眼看出它们是同一类问题，再回头定位到提示词里的那一句话。
2. **看清楚是谁做的决定**。`decision_method` 和 `unconfirmed_ai_assessment` 这两个字段救了一次命——没有它们，会一直以为是模型判错，继续改提示词，越改越糟。
3. **画出来自己看**。饼图标签被裁切这种问题，读代码永远发现不了，把几何渲染成图片看一眼就出来了。
4. **一次只改一个地方，改完立刻验证**。前端每次改完都跑 `npm run build`，后端每次改完都跑离线测试，避免几个改动叠在一起之后无法归因。
5. **不拿答案对着调**。全程不读取主办方的标准答案文件，提示词只依据邮件本身的业务含义修改，避免调成只对这 520 封有效。
